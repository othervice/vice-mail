# Contributing to Vice Mail

Thank you for your interest. Vice Mail is pre-alpha and maintained by one person, so please open
an issue to discuss anything larger than a small fix before you spend time on it. Bug reports with
steps to reproduce are as welcome as code.

Security problems are not reported in public issues; see [SECURITY.md](SECURITY.md).

By contributing you agree that your contribution is licensed under GPL-3.0-or-later, the licence
of the project ([LICENSE](LICENSE)).

## Setting up

The development machine is a Mac with Apple silicon; the Windows installer is cross-built on it.
[docs/SETUP.md](docs/SETUP.md) lists every tool with the tested version and the exact commands.
In short: Xcode or its Command Line Tools, Rust stable (at least 1.98) via rustup, Node.js 24,
pnpm 12, cargo-deny, and Python 3 for the test mail server.

```sh
pnpm --dir app install --frozen-lockfile
pnpm --dir app tauri dev            # run the app in development mode
```

## The check

```sh
scripts/check.sh
```

It must be green before a change is merged. It runs, and stops at the first failure:

- that `unsafe` appears only in `crates/webview2-guard`;
- `cargo fmt --check`, Clippy with warnings as errors (also with the `e2e` feature and, when
  cargo-xwin and LLVM are installed, for the Windows target);
- all Rust tests;
- TypeScript type check, ESLint with no warnings allowed, Vitest, the Vite build;
- `cargo deny` (licences, advisories, banned crates, sources) and `pnpm audit` for the production
  dependencies.

## Tests against the local mail server

Never test against a real mailbox. Integration tests run against a local
[Stalwart](https://github.com/stalwartlabs/stalwart) server that listens only on `127.0.0.1` and
cannot send mail anywhere else ([testmail/README.md](testmail/README.md)):

```sh
scripts/testmail.sh reset && scripts/testmail.sh start && scripts/testmail.sh seed 1000
cargo test --workspace -- --include-ignored     # also runs the tests that need the server
scripts/testmail.sh stop
```

The test accounts `alice@vicemail.test` and `bob@vicemail.test` and their passwords are documented
test values, not secrets.

Desktop tests drive the real app through an embedded WebDriver. They need a logged-in GUI session
and are not part of `scripts/check.sh`:

```sh
pnpm --dir app test:e2e
```

Tests for a new feature go next to the code they test. Behaviour belongs in the crates, where it can
be tested without a web view; `app/src-tauri` stays a thin shell.

## Rules for code

These hold for every change and are checked in review.

**Boundaries**
- The interface talks to the core only through typed commands and events. The generated bindings
  (`app/src/generated/`, which contains `invoke`) and `@tauri-apps/api` are imported only in
  `app/src/services/ipc.ts`. The frontend never touches the database, the file system or the
  network.
- The bindings are generated by tauri-specta and never edited by hand. A test fails when they are
  stale; regenerate them with `UPDATE_BINDINGS=1 cargo test -p mail-app bindings`.
- `app/src-tauri` holds windows, commands and wiring only; logic goes into the crates.
- `mail-model` holds types and traits only, no IO. Adapters such as `mail-imap` know neither the
  interface nor the database. No circular dependencies.
- Every action that changes mail on a server goes through the outbox (the `operation` table) and
  has a visible state.
- HTML from mail is untrusted and is shown only through the pipeline described under "Security
  boundaries" in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).
- `unsafe` is forbidden everywhere except `crates/webview2-guard`, where each use carries its own
  `#[allow(unsafe_code)]` and a `// SAFETY:` comment.

**Data and privacy**
- No invented data in the interface. Without an account the app shows empty states, never sample
  messages.
- No secrets in code, logs, the database or the repository. Passwords and keys live in the system
  keychain; the `Secret<T>` type keeps them out of logs and error messages.
- No network connection except to servers the user has set up. The complete list of allowed
  connections is in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) and
  [docs/PRIVACY.md](docs/PRIVACY.md); a new kind of connection needs a recorded decision and an
  update of both.
- New accounts are read-only (`writes_enabled = false`); the user turns on changes per account.

**Errors**
- Never swallow an error. Errors are typed all the way to the interface and shown there in words a
  user understands.

**Texts and names**
- No interface text inside components. Every string comes from `app/src/i18n/` and exists in
  English (`en.ts`) and German (`de.ts`); ESLint (`i18next/no-literal-string`) enforces it.
- The product name appears in code only in `app/src-tauri/tauri.conf.json` and
  `app/src/config/product.ts`; everything else reads it from there.

**Dependencies**
- A new dependency needs a clear purpose, active maintenance (a release within the last twelve
  months) and a licence compatible with GPL-3.0. Add it to the stack table in
  [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) with its version and the reason.
- TLS goes through rustls, never OpenSSL.

## Language

Code, identifiers, comments, commit messages, the README and the English interface texts are in
English. The project log under `docs/` (plan, stages, decisions, specification, design) is
written in German; see [docs/README.md](docs/README.md).

## Commits

- One commit per finished task, with its tests, and `scripts/check.sh` green.
- The first line says what changed, in plain English, without a trailing period and in about 72
  characters at most (for example "Accounts and folders column replaces the sidebar").
- The body, wrapped at about 72 characters, says why, what it touches and how it was tested.
  Name what was not tested.
- Do not commit generated build output, local data or anything from `design-reference/` (a local,
  ignored folder with third-party material that must never be published).

## Stages and decisions

Larger work is planned in stages: [docs/PLAN.md](docs/PLAN.md) lists them with their status, and
each stage has a file `docs/stages/NN-name.md` with its goal, tasks, acceptance checks, what is
explicitly out of scope, and a "Result" section that records only what was actually run and
checked (anything not checked is named as unchecked).

To add a stage, copy the structure of an existing file, give it the next free number and add a row
to the table in `docs/PLAN.md`.

When an assumption of the plan turns out to be wrong, or a choice with consequences is made, record
it as a decision: `docs/decisions/NNNN-short-title.md` with the next free number, giving the date,
the reason, the status, the affected code and, where it applies, measurements. Then update
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) and any later stage files the decision changes.
A decision is not rewritten afterwards: changes are added as a dated addendum, or a later decision
refers to the earlier one and replaces it.
